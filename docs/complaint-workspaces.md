# 민원별 작성 탭과 계정 저장 적용 안내

2026-10-12, codex/search-wide-layout 브랜치의 로컬 변경입니다. 커밋·푸시·배포·실제 DB 변경은 수행하지 않았습니다.

## 사용 흐름

1. 승인된 개인 계정으로 로그인하고 민원 작성 화면에서 ‘＋ 새 민원’을 누릅니다.
2. 민원마다 탭 이름, 비식별 질의와 답변 방향을 입력합니다. 최대 10개 작업을 유지합니다.
3. 탭을 전환하거나 통합 검색·데이터 관리로 이동해도 각 작업의 작성 상태를 유지합니다. 다른 탭에서 분석 중에도 새 민원을 작성할 수 있습니다.
4. 비식별 질의·답변 방향·초안·AI 선택 근거의 식별자/제목/선택 이유·조문 확인 결과·답변 예정일은 변경 후 약 0.9초 뒤 계정에 저장합니다. 화면을 떠나거나 로그아웃할 때도 저장을 시도합니다. ‘계정에 저장됨’을 확인한 뒤 접속을 종료하세요.
5. 같은 계정으로 다시 접속하면 서버의 최대 10개 민원을 복원합니다. 저장된 초안을 직접 편집할 수 있습니다. AI 재작성은 질의를 다시 확인하고 수락한 뒤 현재 부서 권한으로 근거를 다시 검색합니다.
6. ×를 누르면 확인 후 해당 작성 상태를 삭제합니다. 기존 답변 버전 기록은 별도로 유지합니다.

공개 테스트 계정은 개인 소유자를 구분하지 못하므로 서버 저장을 차단합니다. 이 모드에서는 탭을 현재 접속의 메모리에서만 관리합니다. 브라우저 새로고침이나 종료 후 복원되지 않습니다.

## 저장과 개인정보

민원 원문, 원본 파일, 파일명, 신청/접수번호, 임시 추출 메타데이터, 전송 승인 여부, 서명과 전송용 envelope는 저장 스키마에서 제외합니다. 비식별 작성 필드는 브라우저에서 마스킹한 후 전송하며 서버에서도 알려진 개인정보 패턴을 검사합니다. 자동 마스킹은 모든 개인정보를 보장하지 않으므로 질의를 작성할 때 직접 식별 가능한 세부 사실을 제외해야 합니다.

선택 근거는 당시 선택의 기록입니다. 원문·검색 결과 전문·PDF URL은 저장하지 않습니다. 원문 조회 및 새 AI 작성은 현재 접근 권한으로 다시 수행합니다. 접속을 끊은 후 진행 중인 AI 작업을 서버에서 계속 수행하는 기능은 포함하지 않습니다.

다른 접속이 같은 민원을 수정하면 revision 충돌로 자동 덮어쓰기를 중단합니다. ‘작성 내용 백업’으로 현재의 비식별 상태를 JSON으로 확보한 다음 서버 상태를 다시 불러오세요. 백업은 보관용이며 자동 병합/가져오기 기능은 없습니다. 통신 실패는 ‘계정에 저장됨’으로 표시하지 않으며 ‘지금 저장 / 재시도’로 재시도합니다. 저장 실패/충돌/AI 작업 중에는 로그아웃을 중단하여 내용을 보호합니다. 큰 작성 상태는 브라우저 종료 직전 전송이 보장되지 않으므로 저장 완료 표시를 확인해야 합니다.

## DB 및 사이트 적용 순서

1. 테스트 Supabase에 기존 마이그레이션이 모두 적용되어 있는지 확인합니다.
2. `supabase/migrations/202610120001_complaint_workspaces.sql`을 적용합니다. 기존 테이블/문서/Secrets를 삭제하거나 수정하지 않고 전용 테이블, 소유자 인덱스, service_role 전용 RPC를 추가합니다.
3. 이 변경의 서버·클라이언트 코드를 함께 테스트 사이트에 배포합니다. 개인 계정 복원 검증 환경은 `PUBLIC_TEST_MODE=false`여야 합니다. 기존 Supabase 설정/Secrets를 그대로 사용합니다.
4. 승인된 테스트 사용자 A로 민원 2개를 만들고 각각 다른 질의/답변 방향/초안/예정일을 저장합니다. 탭 전환 및 화면 이동 후 내용을 확인합니다.
5. 로그아웃 후 다시 로그인하고 다른 브라우저에서도 같은 2개 작업이 복원되는지 확인합니다.
6. 사용자 B에게 A의 작업이 보이지 않는지, 비로그인/미승인 계정의 읽기·쓰기가 거절되는지 확인합니다.
7. 10개까지 만든 후 병렬로 11번째 생성을 시도해 제한을 확인합니다. 두 접속에서 같은 revision을 수정하고 충돌 시 덮어쓰기가 중단되는지 확인합니다.
8. 네트워크를 끊고 수정해 저장 실패 표시/내용 유지/재시도를 확인합니다. 서버 상태 재조회 실패 시 현재 편집 내용도 유지되는지 확인합니다.
9. 원문·파일명·민원 식별자·전화번호·AI 서명/envelope가 DB 상태에 없는지 합성 자료로 확인합니다.

테이블은 RLS를 활성화하고 anon/authenticated의 직접 접근을 차단합니다. 서버 API가 승인된 로그인 사용자 소유자로 조회하며 mutation RPC에 전달하는 user_id도 서버가 결정합니다. 변경은 사용자별 advisory transaction lock으로 직렬화해 동시 요청의 10개 제한을 지키고 revision 비교로 충돌을 검출합니다.
