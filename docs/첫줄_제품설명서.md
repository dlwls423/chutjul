# 첫줄 제품 설명서

처음 사용하는 사람을 위한 이용 안내와 기능별 개발 진행상황

기준일: 2026년 9월 6일 · 문서 버전: 1.0 · 코드 기준: `c818ad1`

## 1 첫줄은 어떤 제품인가

첫줄은 개인정보보호위원회 민원 담당자가 과거 민원과 답변, 안내서, 관련 법령을 찾아 새 민원의 답변을 준비하도록 돕는 웹 서비스입니다. 자료를 등록하고, 개인정보를 가린 검색용 자료를 만들고, 필요한 근거를 한 화면에서 확인하는 것이 기본 흐름입니다. 최종 목표는 근거가 연결된 답변 초안을 작성하고 담당자의 검토 결과까지 남기는 것입니다.

**현재는 자료 관리와 검색이 작동하는 개발 중 제품입니다. 새 민원 분석과 답변 초안 화면은 예시 동작이므로, 실제 AI 분석이나 답변 저장이 완료된 기능으로 사용하면 안 됩니다.** 데이터 업로드의 브라우저 AI 요약과 새 민원 분석 화면의 AI 답변 생성은 서로 다른 기능입니다. 전자는 구현되어 있고 후자는 아직 연결되지 않았습니다.

이 문서는 현재 기능과 사용법을 설명합니다. 앞으로 구현해야 할 요구사항과 완료 기준은 별도 문서인 `첫줄_PRD.md`에 정리했습니다.

### 누구를 위한 서비스인가

| 사용자 | 주된 사용 목적 | 권한과 범위 |
| --- | --- | --- |
| 민원 담당자 | 과거 처리 사례와 근거 검색, 자료 등록 및 확인 | 승인된 계정으로 소속 부서 자료 이용 |
| 관리자 | 가입 승인, 부서 변경 승인, 부서별 자료 확인 | 현재 부서 선택 가능, 권한 관리 화면 이용 |
| 테스트 사용자 | 공개 테스트 사이트의 기능 체험 | 테스트부서로 고정된 공용 프로필 |

현재 선택 목록에는 범정부마이데이터추진단, 개인정보보호정책과, 조사총괄과, 개인정보침해평가과, 신기술개인정보과, 분쟁조정과가 있습니다. 테스트부서는 테스트 환경에서 사용합니다. 목록은 코드에 고정되어 있으며 조직도 자동 연동 기능은 없습니다.

### 현재 상태를 읽는 방법

| 표시 | 의미 |
| --- | --- |
| 작동 확인 | 테스트 사이트에서 해당 조회 동작이나 저장된 처리 결과를 직접 확인 |
| 코드 구현 | 화면과 서버 로직이 존재하지만 이번 확인에서 실제 변경 작업까지 실행하지 않음 |
| 부분 구현 | 일부는 구현되어 있으나 연결 누락이나 완료를 막는 제약이 있음 |
| 예시 화면 | 고정 데이터, 임시 안내 또는 화면 내 편집만 제공 |
| 미구현 | 현재 제품의 실행 경로에서 기능을 확인하지 못함 |

‘작동 확인’도 모든 데이터와 환경에서의 품질 보증을 뜻하지 않습니다. 확인 범위는 공개 테스트 사이트와 로컬 코드이며, 운영 사이트 배포 버전과 실제 보안 설정은 별도 확인이 필요합니다.

## 2 현재까지 진행된 내용

### 테스트 사이트에서 확인한 실제 현황

[첫줄 테스트 사이트](https://chutjul-test.leeyejin113.chatgpt.site/)에서 2026년 9월 6일 확인한 값입니다. 데이터가 추가되거나 삭제되면 달라집니다.

| 항목 | 확인 결과 | 해석 |
| --- | --- | --- |
| 접속 프로필 | 테스트 사용자, 테스트부서 | 별도 로그인 없이 테스트 화면 진입 |

| 검색 가능 청크 | 325개 | 화면에 표시된 작업별 청크 수 합계 |

실패 작업에는 `OUTBOUND_PRIVACY_BLOCKED:SERVER_SECONDARY_CHECK`가 표시되었습니다. 이는 해당 작업이 개인정보 재검사에서 중단되었다는 기록이며, 모든 민감정보 탐지가 정확하다는 검증 결과는 아닙니다. 법령 검색 0건 역시 해당 검색의 결과일 뿐, 법령 데이터베이스 전체가 비어 있다는 뜻으로 단정하지 않습니다.

## 3 처음 사용하는 순서

1. **접속과 부서 확인**: 테스트 사이트는 테스트부서로 시작합니다. 일반 환경에서는 회원가입 후 관리자 승인을 받아야 합니다.
2. **통합 검색부터 체험**: 왼쪽 ‘통합 검색’을 누르고 ‘개인정보 전송요구권’ 같은 핵심어를 검색합니다. 기존 자료만 읽으므로 업로드 없이도 제품을 이해할 수 있습니다.
3. **자료 내용 확인**: 유사민원 상세에서 질의와 답변을 읽고, 안내서 상세에서는 검색어가 나온 페이지를 확인합니다.
4. **자료 등록**: ‘데이터 관리’에서 민원 PDF 또는 공개 안내서 PDF를 선택합니다. 현재 Excel은 완료 경로를 보완해야 합니다.
5. **처리 결과 검토**: 완료 여부, 문서와 청크 수, 추출된 질의·답변, 외부 AI 전송자료를 확인합니다. 표시된 처리 성공만으로 추출 내용의 정확성까지 판단하지 않습니다.
6. **새 민원 분석 화면 확인**: 향후 답변 작성 흐름을 살펴볼 수 있습니다. 현재 입력 변경에 따라 분석 결과가 새로 생성되거나 저장되지는 않습니다.

## 4 계정과 부서 이용 안내

### 회원가입과 로그인

일반 환경의 회원가입 화면에서는 이메일, 8자 이상 비밀번호, 이름, 부서, 직급, 회사 전화번호를 입력합니다. 가입 신청 후 상태는 승인 대기이며, 관리자가 승인해야 업무 화면을 이용할 수 있습니다. 반려된 계정에는 반려 안내가 표시됩니다. 로그인, 로그아웃, 세션 갱신은 Supabase 인증과 서버 쿠키를 사용하도록 구현되어 있습니다.

테스트 사이트는 `PUBLIC_TEST_MODE` 설정으로 고정된 테스트 프로필을 제공합니다. 따라서 테스트 화면만으로 실제 회원가입, 로그인, 관리자 승인 또는 로그아웃 이후의 인증 차단을 검증할 수 없습니다. 비밀번호 재설정, 이메일 변경, 계정 탈퇴 화면은 현재 없습니다.

### 내 정보와 부서 변경

사용자 이름을 누르면 ‘내 정보’ 패널이 열립니다. 이름, 직급, 회사 전화번호를 수정할 수 있습니다. 일반 사용자는 현재 부서를 직접 바꾸지 않고 ‘부서 변경 신청’에서 희망 부서와 사유를 제출합니다. 관리자가 승인하면 소속 부서가 변경됩니다. 대기 중인 부서 변경 신청은 중복 접수를 막는 데이터베이스 제약이 있습니다.

### 관리자 권한 관리

관리자에게는 ‘권한 관리’가 표시됩니다. 가입 요청과 부서 변경 요청을 승인 또는 반려하고, 사용자 목록과 처리된 신청 이력을 볼 수 있습니다. 현재 일반 사용자를 관리자로 승격하는 전용 화면은 없습니다.

자료의 접근 범위는 업로드를 소유한 부서가 기준입니다. 민원 원문에서 추출한 ‘처리부서’는 자료 설명용 정보이므로 현재 부서와 다르게 표시될 수 있습니다. 공개 법령은 공통 자료로 검색하도록 구현되어 있습니다. 따라서 ‘현재 부서 자료만 검색’이라는 화면 문구에는 공통 법령 예외를 반영할 필요가 있습니다.

## 5 데이터 관리 이용 안내

### 파일 등록

파일 선택 또는 끌어놓기로 여러 파일을 등록할 수 있습니다. 여러 파일은 하나씩 순서대로 처리되고, 파일별로 대기·처리 중·성공·실패가 표시됩니다. 하나가 실패해도 다음 파일 처리를 이어갑니다. 재처리는 한 파일만 다시 선택합니다.

서버가 허용하는 확장자는 PDF, XLSX, XLS이며 파일당 수신 크기 제한은 100MB입니다. 민원 PDF는 브라우저에서 사본으로 변환한 뒤 전송되므로 원본 파일 크기와 서버가 받는 파일 크기는 다를 수 있습니다.

| 자료 | 현재 처리 방식 | 제약 |
| --- | --- | --- |
| 민원 PDF | 브라우저에서 질의·답변 분리, 개인정보 처리, 요약, 이미지형 마스킹 PDF 생성 | 지원되는 민원 양식, 질의·답변 각각 20자 이상 필요 |
| 안내서 PDF | 파일명에 ‘안내서’가 있으면 안내서로 분류, 서버 텍스트 추출 및 저장 | 파일명만으로 분기하며 공개 자료 여부를 자동 판정하지 않음 |
| Excel | 열 이름 정규화와 민원 행 파서 존재 | 현재 화면은 Excel용 보호 결과를 생성하지 않아 일반 민원 처리 완료 경로가 끊김 |
| 법령 파일 | 유형 표시와 필터는 존재 | 일반 업로드 화면에는 법령 유형 선택 기능이 없으며 공식 API 수집이 별도 경로 |

민원 파일을 처리하려고 이름에 ‘안내서’를 붙이면 보호 처리 경로가 달라집니다. 이 방식은 민원 오류 해결법으로 사용하지 않습니다. 파일명 분기를 명시적 자료 유형과 공개 여부 검증으로 바꾸는 것이 남은 요구사항입니다.

Excel의 권장 열은 `민원제목`, `민원내용`, `답변내용`, `담당부서`, `대분류`, `중분류`, `소분류`, `PDF파일명`입니다. 접수번호, 접수일, 답변일, 담당자, 기관명, 처리상태의 별칭도 매핑 코드에 있습니다. 구형 XLS의 실제 호환성은 별도 검증이 필요합니다. PDF 파일명이 같은 문서를 연결하는 코드도 있지만 현재 Excel 전체 흐름이 완성되었다는 의미는 아닙니다.

### 민원 PDF는 어떻게 처리되는가

**내 기기에서 PDF 읽기 → 질의와 답변 분리 → 개인정보 처리 → 핵심 내용 구조화 → 전송자료 검사 → 마스킹 PDF 생성 → 서버 재검사 → 저장과 임베딩 생성**

브라우저는 이름, 전화번호, 이메일, 주민등록번호, 사업자등록번호, 주소, 법인명 등 정해진 패턴을 탐지합니다. WebGPU를 사용할 수 있으면 브라우저 안에서 소형 AI 모델을 실행합니다. 첫 사용에는 모델 다운로드가 필요하며, 사용할 수 없거나 처리에 실패하면 규칙 기반 보안 요약기로 대체합니다. 원격 AI로 원문을 보내는 대체 경로는 현재 코드에 없습니다.

마스킹 PDF는 페이지를 이미지로 다시 만들어 원래의 텍스트층을 제거합니다. 서버는 업로드된 파일의 해시와 개인정보 검사 결과를 확인하고, PDF에서 추출되는 텍스트가 허용 기준을 넘으면 저장을 차단합니다. 다만 **텍스트층이 없다는 검사와 이미지에 개인정보가 남지 않았다는 검사는 서로 다릅니다.** 현재 서버 검사는 이미지 속 개인정보 전체를 검증하는 OCR 검사가 아닙니다.

답변 본문은 질의와 다른 마스킹 규칙을 사용하며, 현재 답변 처리에는 작성자 이름과 연락처를 중심으로 가리는 제한이 있습니다. 따라서 ‘모든 문서의 모든 개인정보가 제거된다’고 보장하는 기능으로 설명할 수 없습니다.

### 처리 상태 확인

| 단계 | 의미 |
| --- | --- |
| 대기 및 중복 검사 | 작업 생성, 같은 부서의 파일 해시 중복 확인 |
| 브라우저 추출 및 탐지 | 민원 구조 인식과 개인정보 처리 |
| 브라우저 AI 요약 | 목적, 핵심 사실, 법적 질문, 요청 답변, 불확실성 정리 |
| 외부 전송자료 재검사 | 요약문 등에 남은 식별 패턴 확인 |
| 마스킹 PDF 저장 | 민원 PDF 사본 저장, 안내서는 별도 원본 저장 경로 |
| 검색 단위 분할 및 임베딩 | 텍스트를 나누고 검색용 숫자 표현 생성 |
| 처리 완료 | 문서와 청크 저장 완료 |
| 처리 실패 | 상세 오류를 확인해야 하는 상태 |

데이터 목록과 처리 중 상세 화면은 약 2초마다 갱신합니다. 진행률은 단계별 표시값이며, 정확한 남은 시간이나 개발 완료율이 아닙니다. ‘관리자 검토 대기’ 상태 이름과 메타데이터의 ‘검토 대기’는 존재하지만, 사람의 승인으로 다음 처리를 진행시키는 완성된 검토 흐름은 없습니다.

### 상세 보기와 삭제

업로드 행의 ‘상세’를 누르면 현재 상태, 개인정보 탐지 수, 문서 수, 청크 수와 단계별 처리 내용을 봅니다. 여러 문서가 있으면 왼쪽 목록에서 선택합니다.

민원 상세에는 신청번호·접수번호·신청 및 접수 일시·처리완료 예정일·민원요지·처리부서·담당자·처리자·통보일·답변 확인일·민원종류·처리구분·공개여부·처리기간·통지방식·첨부파일 이름·관련 법령 등의 추출 정보가 표시됩니다. 없는 값은 빈칸 또는 ‘—’로 표시합니다. 첨부파일 이름 표시는 첨부파일 자체의 업로드나 열람을 뜻하지 않습니다.

질의와 답변, 로컬 모델, 구조화된 전송 예정자료, 임베딩 청크, 마스킹 본문 및 전체 메타데이터도 확인할 수 있습니다. 안내서 상세는 제목, 페이지 수, 청크 수, 추출된 목차를 표시합니다.

| 동작 | 현재 범위 |
| --- | --- |
| 개별 민원 또는 자료 삭제 | 문서와 연결 청크 삭제. 원래 업로드 파일과 작업 전체를 지우는 동작은 아님 |
| 업로드 자료 전체 삭제 | 관련 문서, 청크, 저장 PDF와 작업 기록 삭제 |
| 재처리 | 실패 행에서 기존 파일명과 같은 파일을 한 개 다시 선택 |

삭제는 현재 복구 기능이 없는 동작입니다. 개별 삭제 뒤 작업 집계값 재계산, 삭제 중 일부 실패의 복구, 재처리의 소유 부서 권한 검증은 보완 항목입니다. 이 문서를 작성하면서 삭제나 재업로드는 실행하지 않았습니다.

## 6 통합 검색 이용 안내

검색창에 핵심어 또는 문장을 입력하고 검색을 누릅니다. 추천 검색은 ‘개인정보 전송요구권’, ‘허가 처리기간’, ‘마이데이터 철회’입니다. 현재 검색은 입력 문장의 의미를 추론하는 방식이 아니라 **공백으로 나눈 단어의 포함 여부와 가중치로 순위를 매기는 키워드 검색**입니다. 긴 문장보다 필요한 핵심어를 줄여 입력하는 편이 결과를 이해하기 쉽습니다.

검색 대상은 제목, 민원요지, 질의, 답변, 마스킹 본문, 검색 청크와 일부 접수 식별 정보입니다. 검색되는 일반 문서는 처리가 완료되어 `ready` 상태인 자료입니다. 법령은 별도 법령 테이블에서 `current` 상태를 검색합니다.

| 기능 | 사용법과 의미 |
| --- | --- |
| 자료 유형 탭 | 전체, 유사민원, 법령, 안내서로 결과를 좁힘 |
| 업무 분류 필터 | 현재 검색 결과에 존재하는 분류로 필터링 |
| 소관 법령 필터 | 결과에 추출된 법령 참조로 필터링 |
| 정렬 | 관련도순 또는 최신순 선택 |
| 일치도 점수 | 키워드 출현과 제목 일치 등으로 계산한 점수. AI 확신도나 정답률이 아님 |
| 강조 표시 | 검색어가 들어간 제목과 문장에 색상 표시 |
| 결과 더보기 | 20건씩 추가 표시, 통합 응답은 최대 100건 |
| 검색 상태 유지 | 메뉴 이동 시 결과와 필터를 메모리에 유지. 새로고침 후 영구 보존은 아님 |
| 빈 결과와 오류 | 검색어를 줄여 재검색하거나 연결 오류 확인 |

민원 상세에서는 질의와 답변 및 처리 정보를 함께 봅니다. 안내서 상세에서는 검색어가 나온 문장과 페이지 목록을 보고 페이지를 선택할 수 있으며, PDF를 새 창으로 열 수 있습니다. PDF 열람 링크는 코드상 15분 유효기간의 서명 URL입니다. 만료되면 상세를 다시 열어야 합니다. 이번 확인에서는 안내서 검색 결과까지 확인했으며 PDF 페이지 이동 전체를 재검증하지는 않았습니다.

‘최신순’은 현재 일반 문서의 등록 시각, 법령의 수집 시각을 바탕으로 정렬됩니다. 민원 접수일이나 법령 시행일순과 같지 않습니다. 상단의 ‘2초마다 자동 갱신’ 문구는 검색 화면에도 보이지만 검색 결과 자체는 검색 실행 시 갱신됩니다.

## 7 법령 자동 현행화

법령 자료를 직접 파일로 올리는 흐름과 별개로, 국가법령정보센터 API에서 지정 자료를 수집하는 코드가 있습니다. 법령·시행령·행정규칙 25개가 초기 수집 대상에 등록되어 있습니다. 모든 대한민국 법령을 수집하는 기능은 아닙니다.

초기 목록은 개인정보 보호법과 시행령, 개인정보 단체소송규칙, 신용정보법과 시행령, 민원 처리법과 시행령, 행정절차법, 개인정보 처리 방법 고시, 표준 개인정보 보호지침, 안전성 확보조치 기준, 과징금 부과기준, 영향평가 고시, 처리방침 평가 고시, 보호수준 평가 고시, 보호책임자 경력 인정 고시, 가명정보 결합 및 반출 고시, 공공기관 가명정보 결합 및 반출 고시, 자율규제단체 지정 운영 규정, 조사 및 처분 규정, 개인정보 전송 및 전문기관 지정 고시, 보건의료 분야 전송 고시, 전기 분야 전송 고시, 국경 간 개인정보 보호 규칙 인증제도 지침, 정보보호 및 개인정보보호 관리체계 인증 고시입니다. 정확한 등록 명칭은 법령 마이그레이션의 `legal_sources` 목록이 기준입니다.

본문 해시가 바뀌면 버전을 추가하고 현행·시행예정·연혁 상태를 보관합니다. 검색은 현행 상태만 이용하며 부서 연관성과 자료 우선순위를 순위에 반영합니다. 설정된 GitHub Actions는 6시간 간격으로 **테스트 사이트** 동기화를 호출합니다. 수동 호출과 최근 실행 상태 조회 API도 있습니다.

현재 상태는 부분 구현입니다. 실제 최근 동기화 성공 기록은 이번 확인에서 확보하지 못했습니다. 또한 같은 본문 해시로 이미 저장된 시행예정 버전이 시행일에 현행으로 전환되는 로직은 보완이 필요합니다. 관리자 화면의 현행화 대시보드, 법령 연혁 비교, 검색 상세의 공식 출처 및 시행일 표시도 완성되지 않았습니다.

## 9 개인정보와 데이터 저장 범위

| 데이터 | 현재 코드상 처리 범위 |
| --- | --- |
| 일반 민원 PDF 원본 바이트 | 정상 브라우저 경로에서는 기기 안에서 처리, 마스킹 PDF로 교체 후 전송 |
| 민원 파일명과 해시 | 서버 작업 정보에 전달·저장. 파일명까지 비식별화되는 것은 아님 |
| 질의·답변과 본문 | 마스킹 처리된 값을 저장하도록 구현. 답변 마스킹 범위와 탐지 품질에는 제약 존재 |
| 민원 마스킹 PDF | 비공개 Storage 사용 전제. 실제 버킷 권한은 배포 설정 확인 필요 |
| 안내서 PDF | 원본 서버 전송 및 Storage 저장 경로 사용 |
| Excel 원본 | 현재 서버로 전송되고 파싱 전 Storage에 저장하는 경로 존재 |
| 외부 AI 입력 | 현재 실행 경로의 외부 AI 호출은 OpenAI 임베딩. 민원 요약 청크 외에 제목·요지 문맥 청크도 포함 |
| 로컬 AI 기록 | 구조화 내용, 모델 이름, 탐지 유형·건수, 검토 상태 등 |

따라서 데이터 관리 화면의 ‘민원 원본은 서버·Storage·DB에 저장하지 않음’ 문구를 Excel, 파일명, 모든 답변 내용에까지 확대해 이해하면 안 됩니다. 서버의 요약 검사는 실제 임베딩에 보내는 제목·요지 등 전체 입력과 완전히 같은 범위를 검사하지 않습니다. 이 차이는 PRD에서 우선 해결해야 할 항목으로 지정했습니다.

이전 문서에는 Python PDF 마스킹 서비스, 원본 격리 저장, Ollama 게이트웨이, OpenAI Responses를 이용한 PDF 추출 방식이 남아 있습니다. 현재 주 실행 경로는 브라우저 보호 처리와 OpenAI 임베딩이며, 이전 방식의 설명을 현재 동작으로 혼용하지 않습니다.

## 10 문제가 생겼을 때

| 상황 | 의미와 대응 |
| --- | --- |
| 이미 등록된 파일 | 같은 부서의 해시 중복. 실패 작업이면 해당 행의 재처리 사용 |
| 질의나 답변을 분리하지 못함 | 현재 지원 양식과 길이 조건에 맞지 않음. 질의와 답변이 포함된 PDF인지 확인 |
| 스캔 페이지 차단 | 브라우저가 확인할 텍스트층이 없음. OCR 텍스트가 포함된 자료 필요. 제품 내부 OCR 기능은 미구현 |
| 개인정보 검사 실패 | 내용을 가리지 않은 채 우회하지 않고 탐지·요약 결과를 점검해야 함 |
| 마스킹 PDF에서 텍스트 추출 | 사본 검증 실패. 새로고침 후 재시도해도 반복되면 구현 점검 필요 |
| Excel 보호 결과 오류 | 현재 Excel의 V2 연결 제약. 사용자가 열 이름만 바꿔 해결할 수 있는 오류가 아님 |
| 모델 준비가 오래 걸림 | 최초 다운로드와 기기 자원 영향. 코드상 생성 타임아웃은 35초이며 화면의 20초 안내와 차이 있음 |
| 검색 결과가 너무 많음 | 단어 하나만 일치해도 포함될 수 있음. 자료 유형·분류·법령 필터 활용 |
| 법령 결과 없음 | 검색어, 현행 버전 저장 여부, 동기화 상태 확인 필요 |
| 빈 데이터인데 예시 목록 표시 | 현재 로딩 전 또는 자료 0건일 때 예시 행이 표시되는 코드가 있음 |
| Supabase 또는 OpenAI 설정 오류 | 서비스 운영자의 연결 설정 필요 |
