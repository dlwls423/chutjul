# 첫줄 제품 요구사항 문서

근거를 확인하며 민원 답변을 준비하는 업무 지원 서비스

기준일: 2026년 9월 6일 · 문서 버전: 1.0 · 현행 코드 기준: `c818ad1`

문서 상태: 현재 구현을 기준으로 작성한 요구사항 초안. 아래 우선순위·목표 지표·출시 단계는 제안이며, 담당자와 일정은 미정입니다.

## 1 제품 목적과 해결할 문제

첫줄의 목적은 민원 담당자가 과거 답변과 유효한 법령·안내서를 찾고, 근거를 확인하면서 새 답변을 작성하도록 돕는 것입니다. 개인정보를 포함한 원문을 외부 AI에 그대로 보내지 않고도 답변에 필요한 사실과 쟁점을 활용하는 것을 핵심 원칙으로 삼습니다.

제품이 해결하려는 문제는 다음과 같습니다. 이는 현재 기능과 설계 의도를 정리한 문제 가설이며, 사용자 인터뷰나 정량 조사로 검증된 성과는 아닙니다.

| 문제 가설 | 제품이 제공할 결과 |
| --- | --- |
| 과거 민원·법령·안내서가 분산되어 근거 탐색에 시간이 듦 | 부서 자료와 공통 법령을 한 번에 검색하고 원문 위치 확인 |
| 답변 작성자가 바뀌면 판단 근거와 맥락을 재구성해야 함 | 저장된 답변에 사용 근거와 검토 이력을 연결 |
| 자료를 AI에 입력하는 과정에서 개인정보와 사업정보가 노출될 수 있음 | 기기 내 보호 처리, 최소정보 구성, 외부 전송 전 서버 검증 |
| 법령 개정과 시행일 변경을 놓치기 쉬움 | 공식 출처 수집, 버전 및 시행 상태 관리 |
| 자료 처리 실패나 요약 오류의 원인을 알기 어려움 | 단계별 상태, 실패 원인, 추출 결과와 전송자료 제공 |

**현재는 자료 등록·검색 기반이 구현된 테스트 단계입니다. 새 민원 분석·답변 생성·저장은 예시 화면 상태이므로, 실제 답변 작성 지원 제품의 출시 완료로 보지 않습니다.**

## 2 사용자와 핵심 시나리오

| 사용자 | 해야 하는 일 | 성공 조건 |
| --- | --- | --- |
| 민원 담당자 | 민원을 읽고 근거를 찾아 답변 초안을 검토 | 사실과 근거를 추적할 수 있는 답변을 저장·재조회 |
| 자료 관리 담당자 | 민원 PDF·Excel·안내서를 등록하고 품질 점검 | 추출 내용과 검색 결과가 연결되고 실패 원인 파악 가능 |
| 관리자 | 가입·부서 변경 승인, 접근 범위 관리 | 승인된 사용자에게 허용된 자료만 노출 |
| 운영 담당자 | 법령 현행화, 배포, 오류와 데이터 처리 관리 | 동기화 실패와 보호 처리 실패를 발견하고 복구 |

운영 담당자는 책임 역할의 제안이며, 현재 제품에 별도 권한 값으로 존재하지 않습니다. 현재 권한 값은 `admin`, `user`입니다.

### 목표 사용자 여정

1. 사용자가 가입하고 관리자가 소속 부서를 승인한다.
2. 담당자가 부서의 과거 민원 자료와 공개 안내서를 등록한다.
3. 브라우저가 민원 원문을 보호 처리하고, 서버가 결과를 다시 검사한다.
4. 담당자가 추출된 사실·질문·답변과 전송 예정자료를 확인하고 수정·승인한다.
5. 사용자가 새 민원을 입력하고 보호 처리를 거친다.
6. 시스템이 부서 자료와 공통 법령을 검색하고 소관·분류·쟁점을 제안한다.
7. 담당자가 근거를 선택한 뒤 답변 초안을 생성·수정한다.
8. 답변과 근거 버전, 작성자, 검토 결과를 저장하고 다시 조회한다.

4번의 사람 검토와 5~8번의 실제 분석·생성·저장 연결은 현재 완성되지 않았습니다.

## 3 범위와 우선순위

P0는 실제 민원 자료를 이용하는 출시 전에 해결해야 할 조건, P1은 답변 작성 지원 MVP를 완성하는 기능, P2는 이후 확장으로 제안합니다. 일정이나 인력 투입 승인을 의미하지 않습니다.

| 우선순위 | 포함 범위 |
| --- | --- |
| P0 | 원본 저장 정책 통일, 전체 외부 입력 검사, 부서 권한 통일, 사람 검토 경계, 예시와 실제 상태 구분, 데이터 삭제·재처리 안전성, 법령의 현행성 검증 |
| P1 | Excel 완성, 검색 품질·페이지 처리, 실제 민원 분석, 근거 선택, 초안 생성과 저장, 이력, 오류·운영 상태 표시, 기본 접근성 |
| P2 | 벡터와 키워드 결합 검색 고도화, OCR 내장, 법령 연혁 비교, 실제 이관·일정 알림, 내보내기, 조직도 연동, SSO 등 별도 요구에 따른 확장 |

MVP의 범위 밖은 국민신문고 등 외부 민원 시스템 자동 접수·발송, 담당자 검토 없는 법적 판단 확정, 전 기관 자료 무제한 공유, 결제·구독입니다. 소관 판단과 분류는 담당자에게 제안하는 기능이며 최종 처분이나 공식 회신을 자동 확정하지 않습니다.

## 4 현재 구현 기준선

## 5 기능 요구사항과 수용 기준

### R01 계정과 세션

우선순위 P0 · F01 F05

일반 환경에서는 이메일·비밀번호로 로그인하고, 가입 신청은 승인 대기로 시작한다. 승인 전 계정과 반려 계정의 업무 자료 접근을 차단한다. 세션 만료와 갱신 실패 시 안전하게 로그인 상태로 돌아간다. 테스트 모드는 테스트 자료와 환경에 한정한다.

수용 기준: 미로그인 요청은 업무 API에서 401, 미승인 요청은 403으로 거절한다. 승인·반려·세션 만료·로그아웃을 실제 계정으로 검증한다. 운영 환경에서 공용 테스트 프로필이 활성화되지 않음을 배포 검사로 확인한다. 승인되지 않은 관리자가 관리자 기능을 실행할 수 없는지도 검사한다.

### R02 내 정보와 관리자 승인

우선순위 P1 · F02 F03

사용자는 이름·직급·회사 전화번호를 수정하고 부서 변경을 신청한다. 관리자는 가입과 부서 변경을 승인·반려하며 사용자 목록과 이력을 조회한다. 권한 승격은 기존 사용자 정보 수정과 분리한다.

수용 기준: 필수값 오류와 중복 신청은 사용자에게 표시된다. 승인 시 요청 상태와 소속 부서가 일관되게 반영된다. 이미 처리한 요청의 중복 처리를 차단한다. 요청일과 처리일, 처리자를 구분해 기록한다. 관리자 API 실패를 성공처럼 표시하지 않는다. 부서 목록은 가입·관리자 선택·법령 메타데이터 간 기준을 통일한다.

### R03 소유 부서에 따른 접근 제어

우선순위 P0 · F04

자료의 접근 권한은 `source_files.owning_department`를 기준으로 한다. 민원에서 추출한 처리부서는 설명 정보로 취급한다. 일반 사용자가 조회 매개변수나 문서 ID를 바꾸어 다른 부서 자료에 접근하지 못하게 한다. 공통 공개 법령은 별도 범위로 표시한다.

현재 격차: 검색과 업로드 상세는 소유 부서를 기준으로 하지만 개별 문서 삭제는 문서의 처리부서를 검사한다. 재처리 함수는 전달된 작업의 소유 부서를 확인하지 않는다. 일부 구버전 DB 호환 분기는 부서 필터 없는 조회로 대체한다. 검색 캐시는 부서나 사용자 키가 없다.

수용 기준: 목록·상세·검색·PDF·개별 삭제·전체 삭제·재처리를 두 부서의 계정으로 교차 검사해 허용되지 않은 요청이 모두 차단된다. 부서·계정 변경 즉시 기존 검색 결과와 상세 캐시를 지운다. 필요한 DB 컬럼이 없을 때 접근 범위를 넓히지 않고 서비스 오류로 중단한다. 관리자 권한은 각 API에서 별도로 검증한다.

### R04 파일 접수와 중복 검사

우선순위 P1 · F06 F07

PDF와 검증된 Excel 형식을 선택 또는 끌어놓기로 접수하고 여러 파일을 순서대로 처리한다. 자료 유형은 사용자가 명시적으로 선택하며, 안내서의 공개 자료 여부를 확인한다. 파일명만으로 민원 보호 처리를 건너뛰지 않는다.

수용 기준: 파일당 서버 수신 100MB 제한과 브라우저 처리 가능 조건을 안내한다. 확장자와 실제 형식을 확인한다. 동일 부서의 동일 파일은 중복 처리하지 않고 기존 작업을 안내한다. 파일 하나가 실패해도 나머지 결과가 보존된다. 동일 요청의 반복 실행으로 작업과 청크가 중복 생성되지 않는다. 파일명에 포함된 식별정보의 저장 정책을 적용한다.

### R05 민원 PDF 구조 추출

우선순위 P1 · F08

지원 양식의 질의·답변과 신청·접수·처리 정보를 분리한다. 추출 불가와 값 없음, 탐지에 의한 마스킹을 구분해 표시한다. 자료 등록용 과거 민원은 현재와 같이 질의와 답변을 모두 요구하되, 새로 접수된 미답변 민원은 별도 분석 입력으로 처리한다.

수용 기준: 기본형·번호 문단·다른 기관 답변형·복수 페이지 자료에서 질문과 답변 경계가 보존된다. 현재 최소 길이 조건인 각각 20자와 양식 오류를 안내한다. 부서명에 담당자 문자열이 붙거나 제목에 첨부파일 목록이 섞이는 경우를 평가셋에 넣는다. 텍스트 없는 스캔은 원문 전송 없이 중단한다. OCR 내장은 P2로 분리한다.

### R06 개인정보 처리와 마스킹 PDF

우선순위 P0 · F09 F11

민원 원본 바이트를 브라우저 밖으로 보내지 않는 원칙을 정상 PDF 경로뿐 아니라 모든 민원 수집 형식에 일관되게 적용한다. 질의·답변·제목·파일명·메타데이터·PDF 이미지 각각의 보호 범위를 명확히 한다. 서버는 브라우저의 안전 선언을 그대로 신뢰하지 않고 실제 전송·저장 대상에 맞는 검사를 수행한다.

현재 격차: 답변은 서명 중심의 제한된 마스킹을 사용한다. PDF 텍스트층 부재 검사만으로 이미지 속 개인정보 제거를 보증할 수 없다. 요약문 검사는 제목과 전체 메타데이터의 검사와 다르다. 안내서는 파일명으로 보호 경로에서 제외되고 Excel은 원본 저장 경로를 사용한다.

수용 기준: 이름·전화·이메일·주민번호·주소·법인명·사업자번호·계좌·카드·신청 식별정보를 포함한 합성 자료를 질의와 답변 양쪽에 배치해 검증한다. 외부 요청과 저장 대상에 금지 정보가 남으면 중단한다. PDF는 텍스트 추출 검사와 페이지 이미지 검토를 모두 통과한다. 해시 불일치, 조작된 보호 결과, 개인정보를 넣은 제목도 거절한다. 탐지 유형과 위치 등 필요한 기록만 남기고 원문 값을 오류 로그에 기록하지 않는다.

### R07 최소정보 구조화와 사람 검토

우선순위 P0 · F10 F32

구조화 결과는 목적, 핵심 사실, 법적 질문, 요청 답변, 불확실성으로 구성한다. 브라우저 로컬 AI와 규칙 기반 대체를 구분한다. 사람의 검토가 필요한 자료는 초안 생성뿐 아니라 외부 임베딩 전송 이전에 검토 경계를 갖도록 한다.

수용 기준: 원문의 사실·부정 표현·전제·예외 조건을 보존하고 없는 사실을 만들지 않는다. 모델 다운로드 실패·WebGPU 미지원·생성 시간 초과 시 대체 모드 또는 검토 대기로 명시한다. 담당자가 수정·승인·반려할 수 있고 승인자·시각·승인한 데이터 해시를 저장한다. 승인 이후 내용이 바뀌면 재검토한다. 미승인 자료는 외부 전송하지 않는다. 진행 안내와 실제 타임아웃을 일치시킨다.

현재 `review_status: pending` 값만 저장되고 임베딩은 이미 실행되므로, 현 상태를 승인 절차가 구현된 것으로 간주하지 않는다.

### R08 문서 저장과 임베딩

비식별 문서, 검색 청크, 벡터 및 필요한 출처 정보를 저장한다. 외부 AI는 승인된 최소정보만 받으며, 제목·민원요지 문맥 청크까지 포함해 **실제 API 입력 전체**를 검사한다. 임베딩은 현재 `text-embedding-3-small` 기본값을 사용하며 모델 변경 시 벡터 차원 및 기존 인덱스 호환성을 관리한다.

수용 기준: 모든 임베딩 요청 직전에 최종 조립 입력을 검사한다. 청크 저장까지 끝난 문서만 검색 가능으로 전환한다. 일부 배치 실패 시 불완전 자료가 검색되지 않으며 재처리로 복구할 수 있다. 모델명은 환경변수 이름이 아닌 실제 사용 모델을 기록한다. 외부 요청 감사에는 해시·시각·모델·허용 여부를 남긴다. 화면의 ‘전송 예정’과 ‘전송 완료’를 실제 상태와 일치시킨다.

### R09 Excel 처리 완성

민원제목·민원내용·답변내용·담당부서·분류·PDF파일명 등의 열을 행별 문서로 변환한다. PDF와 동등한 개인정보 처리 및 행별 검증 구조를 마련한다.

현재 격차: 화면은 Excel에 `browserPrivacy`를 만들지 않는데 서버는 일반 민원 처리에서 이를 필수로 검증한다. 원본 Excel을 서버에 저장한 뒤 실패할 수 있다. 하나의 PDF용 보호 결과를 모든 Excel 행에 재사용하는 방식은 요구사항을 충족하지 않는다.

수용 기준: 지원 형식을 XLSX와 실제 검증된 XLS로 명시한다. 각 행에 독립된 추출·보호·검토 결과를 갖는다. 헤더 오류·빈 시트·질의·답변 누락·일부 행 실패를 구분한다. 실패한 민원 Excel 원본이 Storage에 남지 않는다. 파일명 연결은 같은 소유 부서의 올바른 PDF에만 적용되고 이전 출처 관계를 손상하지 않는다.

### R10 안내서 저장과 원문 열람

수용 기준: 페이지 수와 검색 위치가 원본과 일치한다. 목차가 없더라도 본문 검색은 가능하며 목차 미추출을 별도로 안내한다. PDF 서명 링크가 만료되면 다시 조회한다. 권한이 없는 사용자는 링크 발급을 받을 수 없다. 추출 실패를 정상 저장으로 표시하지 않는다. 새 창 보기와 좁은 화면에서도 페이지 이동을 사용할 수 있다.

### R11 처리 현황과 상세

우선순위 P1 · F15 F16

업로드 건수, 청크 수, 처리 중·실패 수와 파일별 상태를 보여준다. 상세에서 문서를 선택하고 추출 정보, 개인정보 처리 결과, 전송 내용과 오류를 확인한다.

수용 기준: 로딩·오류·실제 자료 0건·예시 자료를 명확히 구분한다. 단계는 실제 작업 순서와 일치하고 진행률이 임의로 뒤로 이동하지 않는다. 완료 후 갱신을 멈추고 오류 후 재조회 수단을 제공한다. 안내서 상세의 저장 성공 문구도 실제 상태를 따른다. 데이터 목록 페이지 이동은 서버 조회 범위를 포함해 작동한다.

### R12 재처리와 삭제

우선순위 P0 · F17

실패 작업의 소유 부서를 확인한 뒤 파일 재선택으로 재처리한다. 개별 문서 삭제와 업로드 전체 삭제를 구분한다. 복구 불가 삭제의 범위를 실행 전에 명시한다.

수용 기준: 다른 부서 작업 ID로 재처리할 수 없다. 파일명뿐 아니라 파일 내용 변경 여부와 처리 버전을 기록한다. 재시도 횟수는 누적한다. 개별 삭제 후 작업·파일의 문서 수와 청크 수가 정확히 반영된다. 전체 삭제는 DB와 Storage의 완료 여부를 추적하며 일부 실패 후 안전하게 재시도할 수 있다. 이미 없는 Storage 객체는 적절하게 처리하되 다른 오류를 무시하지 않는다. 삭제된 자료는 검색과 캐시에서 제거된다.

### R13 통합 검색과 민원 상세

우선순위 P1 · F18 F19 F20

부서 민원·안내서와 공통 법령을 검색하고 자료 유형·업무 분류·관련 법령으로 좁힌다. 제목·문장 강조, 관련도·최신순, 20건 단위 더보기, 상세 조회를 제공한다. 현재 키워드 검색의 범위와 한계를 UI에 설명한다.

수용 기준: 검색 점수를 신뢰도 확률로 표시하지 않는다. 검색어 없음·결과 없음·연결 오류를 구분한다. 부서와 사용자가 바뀌면 기존 결과를 비운다. 서버의 결과 최대 수와 전체 건수를 구분하고 조회 한도로 자료가 조용히 누락되지 않게 한다. 등록일·접수일·시행일 중 정렬 기준을 명시한다. 민원 상세에서 질문·답변·처리 정보와 출처를 확인한다. 검색 결과 자동 갱신 여부가 안내와 일치한다.

벡터와 키워드를 함께 쓰는 검색은 현재 DB 함수와 임베딩 기반이 있으나 UI 검색에는 연결되지 않았다. P2에서는 별도 평가셋에서 개선 효과가 확인될 때 도입한다.

### R14 공식 법령 수집과 버전 관리

우선순위 P0 · F22

등록된 법령·시행령·행정규칙을 공식 API에서 수집하고 공포·시행일, 원문, 조문 위치와 버전을 보관한다. 현재 초기 대상은 25개이며, 추가·제외는 자료 관리 정책으로 결정한다.

수용 기준: 정확한 법령 식별자로 본문을 연결하고 목록·상세 API의 오류 응답을 정상 법령으로 저장하지 않는다. 법령명 유사 일치로 다른 자료를 선택하지 않는다. 조·항·호·목과 가지 조문을 정확하게 보존한다. 동일 본문 재수집은 중복 버전을 만들지 않는다. 시행예정 버전은 본문 해시가 그대로여도 시행일에 현행으로 전환된다. 새 버전과 조문 저장 실패로 이전 현행이 사라지지 않도록 원자적 처리 또는 복구를 제공한다. 표준 시간대 기준을 명시한다.

### R15 법령 검색과 동기화 운영

우선순위 P0 · F23 F24

현행 자료를 공통 근거로 검색하고, 공식 출처·시행일·버전·수집 시각을 사용자에게 보여준다. 관리자는 자료별 마지막 성공과 오류, 실행 상태를 확인한다. 정기 동기화와 수동 실행 권한을 구분한다.

수용 기준: 같은 법령의 연혁과 시행예정 자료는 기본 현행 검색에 섞이지 않는다. 실제 운영·테스트 대상이 설정으로 구분된다. 일부 실패, 변경 없음, 전체 실패를 정확하게 집계한다. HTTP 200 응답이어도 본문이 실패·부분 실패이면 모니터링에서 발견한다. 법령 자료가 없거나 오래되었으면 사용자가 알 수 있다. 검색 상세에서 공식 링크를 열 수 있고, 초안 저장 시 사용한 버전을 고정한다.

### R16 새 민원 입력과 분석

우선순위 P1 · F25 F26

제목·본문·접수일·담당자를 입력하고 보호 처리 후 실제 분석을 실행한다. 본문은 최대 10,000자로 검증한다. 분석은 소관 후보, 업무 분류, 핵심 쟁점, 추가 확인사항, 신규 유형 가능성을 제시한다.

수용 기준: 입력을 바꾸면 분석 요청과 결과가 해당 입력에 연결된다. 화면의 개인정보 탐지가 실제 탐지 결과를 반영한다. 실패·정보 부족·취소 또는 중복 요청을 처리한다. 고정 점수와 고정 완료 시간을 제거한다. 담당자가 분석을 수정할 수 있다. 새 민원 첨부 기능을 제공한다면 동일 보호 경로를 통과해야 하며, 미구현 상태라면 활성 버튼을 노출하지 않는다.

### R17 근거 선택과 답변 초안

우선순위 P1 · F27 F28

분석 결과를 이용해 부서의 유사민원과 공통 법령·안내서를 추천한다. 담당자가 근거를 추가·제외하고 그 근거로 답변 초안을 생성·재생성·편집한다.

수용 기준: 선택된 근거 ID와 버전·조문·페이지가 실제 생성 입력에 반영된다. 근거가 부족하면 단정적인 답변 대신 확인 필요사항을 표시한다. 생성 문장의 사실과 인용을 원자료로 추적할 수 있다. 원문 개인정보를 외부 모델에 보내지 않는다. 재생성 전에 기존 편집 내용을 보존하거나 덮어쓰기 범위를 알려준다. 화면 편집과 서버 생성 상태를 분리한다. 답변 생성 모델과 요청 저장 정책은 구현 시 결정·검증한다.

### R18 답변 저장과 분석 이력

우선순위 P1 · F29

민원 입력의 보호 처리본, 분석 결과, 선택 근거, 초안과 최종 편집본, 작성자·검토자·시각을 저장한다. 분석 기록에서 다시 열 수 있어야 한다.

수용 기준: 저장 성공은 서버 저장 확인 후 표시한다. 새로고침과 재로그인 후 동일 답변과 근거 버전을 조회한다. 권한 범위를 적용하고 동시 편집 충돌을 처리한다. 수정 이력을 추적하며 사용 근거가 개정되거나 삭제되어도 당시 인용을 식별할 수 있다. 이관 부서와 답변 예정일은 MVP에서 기록값으로 저장하고, 실제 이관 실행과 일정 알림은 P2로 구분한다.

현재 `db/schema.ts`의 `answer_logs` 정의만으로 이 요구사항을 충족하지 않는다. 실제 주 저장소인 Supabase와의 연계 또는 저장소 통합 결정을 먼저 수행한다.

## 6 데이터와 시스템 구조

### 현재 실행 구조

브라우저 React 화면이 사이트의 Edge API를 호출하고, API가 Supabase 인증·데이터베이스·Storage와 통신한다. 민원 PDF의 파싱과 AI 구조화는 브라우저에서 수행한다. 서버는 OpenAI 임베딩 API를 호출한다. 법령 수집은 국가법령정보센터 API를 사용하고 GitHub Actions가 정기 호출하도록 구성되어 있다.

브라우저 AI는 현재 `Qwen2.5-0.5B-Instruct-q4f16_1-MLC`를 사용한다. 답변 생성용 외부 AI 호출은 현재 주 실행 코드에 없다. 로컬 Python 게이트웨이와 PDF 마스킹 서비스는 이전 구조의 보조 구현으로 남아 있으며, 이번 MVP의 필수 운영 서비스로 전제하지 않는다.
